DNS Settings

Configure advanced DNS behavior

Never forward non-FQDN queries

Tells Ferrous DNS to never forward queries for plain names, without dots or domain parts, to upstream nameservers. If the name is not known from local-records or DHCP then a "not found" answer is returned.

If Conditional Forwarding is enabled, unticking this box may cause a partial loop.

Never forward reverse lookups for private IP ranges

All reverse lookups for private IP ranges (i.e., 192.168.0.x/24, etc.) which are not found in local-records or the DHCP leases are answered with "no such domain" rather than being forwarded upstream.

The set of prefixes affected is the list given in RFC6303.

Block local domain from internet

When a local domain (e.g. lan) is configured, queries for that domain that are not found in local records will return NXDOMAIN instead of leaking to your upstream DNS servers.

With a Local DNS server set below, names under the local domain are asked to your router.

Queries for *.lan not in local records will return NXDOMAIN

Local DNS server (optional)

Your router or DHCP server. Ferrous DNS asks it for the hostnames of discovered clients (e.g. device.lan), for names under the local domain, and for the hostnames in your upstream servers (e.g. dns.adguard-dns.com).

Set it when this machine uses Ferrous DNS as its own resolver: without it, upstream hostnames cannot be looked up at startup and those upstreams stay unusable.

An IP address, or IP:port; port 53 when omitted.

Blocked query response

How blocked domains (blocklist, DGA, tunneling, C2) are answered. Null IP returns a cacheable 0.0.0.0/:: so clients stop re-querying — recommended. REFUSED is the legacy mode and makes clients retry aggressively.

How long clients cache the Null IP answer.

Custom A target for blocked domains. Leave empty for 0.0.0.0.

Custom AAAA target. Leave empty for ::.

Point the sinkhole at this server's LAN IP if it serves a block page. Avoid loopback (127.0.0.1 / ::1) — it resolves to each client's own machine, not this server.

DNS64 (NAT64 AAAA synthesis)

Synthesize AAAA records from IPv4-only domains so IPv6-only clients reach them through a NAT64 gateway (RFC 6147). Requires a NAT64 gateway on your network — without one, IPv6-only clients break. Takes effect after a restart.

Must be a /96 prefix. Use the well-known 64:ff9b::/96 unless your NAT64 gateway uses a custom one.

Parallel

Sends the query to all upstream servers simultaneously and returns the fastest response. Best latency at the cost of higher network usage.

Latency: Best Network: High

Balanced

Distributes queries across upstream servers in round-robin order, spreading load evenly across all configured servers.

Latency: Medium Network: Medium

Failover

Queries always go to the primary server. Automatically switches to the next server only when the primary becomes unreachable.

Latency: Depends Network: Low

General Settings

Core DNS resolution behavior settings.

DNSSEC Validation

Validates DNSSEC cryptographic signatures on upstream responses to protect against DNS spoofing and cache poisoning. Off: no validation. Permissive: validate and tag every answer without changing it. Strict: reject (SERVFAIL) answers that fail validation (Bogus), unless the client sets the CD bit.

Requires upstream servers that support DNSSEC. May slightly increase response latency due to signature validation overhead.

mDNS Device Discovery

Listens for mDNS/Bonjour announcements on the local network (UDP 5353, multicast) and names clients after the host name their device announces, such as iPhone-de-Ana, in the Clients page, the query log and the dashboard. A device can only name itself, and a name you set by hand is never replaced.

Requires the server to reach the LAN multicast group (in Docker, host networking). Takes effect after a server restart. Off by default.

Enable DNS Cache

Stores DNS responses in memory so repeated queries are answered instantly without contacting upstream servers. Dramatically reduces resolution latency for frequently accessed domains.

Disable only for debugging purposes. Detailed cache configuration is available in the Cache Settings tab.

URL schemes accepted in the server address fields below. Every protocol accepts a hostname or an IP address.

Unencrypted Fastest Port 53

TLS (DoT)

tls://dns.google:853

DNS over TLS (RFC 7858). Wraps standard DNS in a TLS tunnel. Widely supported with good tooling.

Encrypted TCP Port 853

HTTPS (DoH)

https://dns.google/dns-query

DNS over HTTPS (RFC 8484). Queries sent as HTTP/2 POST. Blends with web traffic — hard to block.

Encrypted TCP · HTTP/2 Port 443

QUIC (DoQ)

doq://dns.adguard-dns.com:853

DNS over QUIC (RFC 9250). TLS 1.3 over UDP. No head-of-line blocking. Best encrypted option overall.

Encrypted UDP · QUIC Port 853

H3 (DoH3)

h3://dns.google/dns-query

DNS over HTTP/3. Same semantics as DoH but over QUIC. Requires UDP port 443 to be reachable.

Encrypted UDP · HTTP/3 Port 443
Writing a server address
  • Prefer the hostname for encrypted protocols. For DoT, DoQ, DoH and H3 it is also the name checked against the server's certificate and sent as SNI; some providers, such as AdGuard DNS private servers, identify you by it.
  • Ports: udp://, tcp://, tls:// and doq:// need one (53 for plain DNS, 853 for DoT and DoQ); https:// and h3:// default to 443. IPv6 addresses go in brackets: doq://[2a10:50c0::ad1:ff]:853.
  • Coming from AdGuard? Its quic://host addresses are written here as doq://host:853.
  • Hostnames are looked up through the Local DNS server (DNS Settings) when one is set, otherwise with this machine's resolver, when the server starts and when pools are saved. A lookup that fails is retried automatically.

Cache Configuration

Configure how DNS responses are stored and managed in memory to minimise upstream queries and latency.

Enable DNS Cache

Stores DNS responses in memory so repeated queries are answered instantly without contacting upstream servers. Dramatically reduces latency for frequently accessed domains.

Default Cache TTL

Time-to-live applied to cached entries that carry no TTL of their own. Does not override TTLs already present in upstream responses.

seconds

Minimum Cache TTL

Floor applied to every cached entry. Upstream values below this threshold are raised to this minimum. Short TTLs are renewed more often, so a higher floor sends fewer refresh queries upstream.

seconds

Maximum Cache TTL

Ceiling applied to every cached entry. Upstream values above this limit are capped to this maximum. Prevents stale entries from persisting indefinitely in the cache.

seconds

Maximum Cache Size

Upper limit on the number of DNS records held in memory. When full, the configured eviction strategy determines which entries are removed to make room for new ones.

entries

Eviction Strategy

Algorithm used to select which cache entries are removed when the cache reaches its size limit.

LRU — Least Recently Used

Removes the entry that was accessed least recently. Simple and predictable — entries not queried for a while are first to go. Well suited for workloads where recent access reliably predicts future demand.

LFU — Least Frequently Used

Removes entries with the lowest total hit count. Keeps the most-queried domains in cache indefinitely. May cause cache pollution where old popular entries crowd out newer, more relevant ones.

LFU-K — Adaptive

Uses the K most recent access timestamps to compute frequency, making it responsive to shifting access patterns. Balances LFU's popularity bias with LRU's recency awareness for adaptive workloads.

Hit Rate Based  (recommended)

Scores entries by hits relative to their TTL. A frequently queried short-TTL record scores higher than one with equal hits but a longer TTL. Ideal for DNS — correctly values CDN and dynamic records that matter most.

Optimistic Refresh

Proactively re-fetches cache entries in the background before they expire, so clients always receive a fresh response with zero added latency. Each entry is renewed at the Refresh Threshold of its TTL, or 60 seconds before it expires, whichever comes first. An entry whose TTL is under a minute is renewed only while clients keep asking for it.

Every entry in use is renewed on its own timer, with at most 16 renewals running at once — there is no rate to tune. The thresholds below only decide which entries go first when more fall due at once than run in parallel.

Refresh Threshold

Fraction of a cache entry's TTL that must have elapsed before a background refresh is triggered. A value of 0.75 refreshes a one-hour entry after 45 minutes. When that would leave less than a minute, the entry is refreshed 60 seconds before it expires instead, but never before half its TTL: a 200-second entry is refreshed after 140 seconds.

0.1 – 0.99

Minimum Hit Rate

Cache hits per minute, counted since the entry's last renewal, below which an entry ranks as cold. Cold entries are still refreshed normally; they only wait behind hot ones when more entries fall due at once than the refresh worker runs in parallel.

hits / min

Minimum Frequency

Lifetime hits below which an entry ranks as cold, alongside Minimum Hit Rate. Keeps a burst of newly inserted entries from jumping ahead of an established working set when more entries fall due at once than the refresh worker runs in parallel.

total hits

Access Window

Time window within which an entry must have been accessed at least once to remain eligible for optimistic refresh. An entry not accessed within this window is left to expire rather than being proactively renewed; the next query for it puts it back on the refresh schedule.

Example: 7200 = 2 h  ·  43200 = 12 h  ·  86400 = 24 h.

seconds

Compaction Interval

How long an entry whose renewal failed, for example on an upstream timeout, waits before its renewal is tried again. Lower values retry sooner; higher values ask a failing upstream less often. Expired entries leave the cache on their own, the second they can no longer be served.

seconds

Malware Detection

Detect DNS-borne malware activity: data tunneling, algorithmically generated domains, rebinding, NXDOMAIN hijacking and known command-and-control servers. Changes apply after a restart.

Enable Malware Detection

Master switch for the five detectors below. Turning it off skips them all; each keeps its own setting for when you turn it back on.

Exemptions

To clear a false positive, allow the domain in DNS Filter, in the group of the clients it is for, or click Allow on its row in the Query Log. To exempt a client such as a monitoring server, put it in a group and switch Malware Detection off for that group in Groups. Both apply at once, with no restart.

DNS Tunneling Detection

Spots data exfiltration and command-and-control channels hidden inside DNS queries (iodine, dnscat2, Cobalt Strike). Phase 1 checks every query instantly; phase 2 scores the traffic of each client and domain in the background.

Enable DNS Tunneling Detection

Run both detection phases on every query.

Action

Block answers with the Block Mode set in DNS Settings and logs the query. Alert resolves normally and only logs the detection: run it for a few days to check for false positives first.

Block NULL Queries

Phase 1: flags NULL (type 10) record queries, which ordinary software never sends and tunneling tools such as iodine use to carry data.

DGA Detection

Flags algorithmically generated domains that malware (Conficker, Mirai, Emotet) uses to find its command-and-control servers. Phase 1 scores each name instantly; phase 2 adds letter-pair analysis and each client's rate of such names in the background.

Enable DGA Detection

Score every queried domain for signs of being machine-generated.

Action

Block answers with the Block Mode set in DNS Settings and logs the query. Alert resolves normally and only logs the detection.

DNS Rebinding Protection

Blocks answers where a public domain resolves to a private or loopback address, so a web page cannot turn your browser against devices on your own network.

Enable DNS Rebinding Protection

Check every answer for private addresses. A blocked answer uses the Block Mode set in DNS Settings. Names under the local domain, answers from the local DNS server and internal pools are always exempt; allow any other split-horizon name, such as a VPN or router page, in DNS Filter.

NXDomain Hijack Detection

Detects upstream resolvers, usually an ISP's, that answer non-existent names with the address of an ad or search page, and turns those answers back into NXDOMAIN.

Enable NXDomain Hijack Detection

Probe each upstream with random .invalid names in the background, and check every answer for the hijack addresses found.

Action

Block rewrites a hijacked answer to NXDOMAIN. Alert passes it through and only logs it.

Response IP Filtering

Blocks answers that resolve to known command-and-control server addresses, taken from threat feeds such as abuse.ch Feodo Tracker and SSL Blacklist. Off by default: it needs at least one feed.

Enable Response IP Filtering

Check the addresses in every answer against the downloaded feeds.

Action

Block answers with the Block Mode set in DNS Settings and logs the query. Alert resolves normally and only logs the match.
